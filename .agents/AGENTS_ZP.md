# AI Image Asset Pipeline Rules

## Image Asset Generation Workflow

When the user asks to generate UI/game image assets, always use the `image_assets` MCP server.

Default workflow:
1. Use `image_assets.start_image_generation_job` to start image generation.
2. Do not use any synchronous image generation tool unless the user explicitly requests it.
3. After receiving `jobId`, call `image_assets.get_image_generation_job` at most once in the same response.
4. If the job status is `succeeded`, return only `imagePath`, `metadataPath`, and a short note.
5. If the job status is `preview_succeeded`, return the preview `imagePath`, `metadataPath`, and `jobId`, then wait for user approval.
6. If the job status is `running` or `pending`, stop polling immediately, return the same `jobId`, and tell the user they can ask to continue/query later.
7. If the user later asks to continue/check/query, call `image_assets.get_image_generation_job` with the same `jobId`; do not start a new job.
8. If the user approves a preview, call `image_assets.promote_image_generation_job` with the same `jobId`, then call `get_image_generation_job` at most once. If it is still running, return the `jobId`.
9. If the job status is `failed`, return the full `error` field.
10. Never regenerate the same `assetName` unless the user explicitly asks for reroll/regenerate/重新生成. If an output PNG already exists, list/return it instead of starting another job.
11. Do not call Unity MCP unless the user explicitly asks to import, bind, place, or build UI in Unity.
12. Do not modify Prefabs, scripts, scenes, or Project Settings during image generation.

Default image generation parameters:
- provider: `openai`
- model: `gpt-image-2`
- size: `1024x1024`
- quality: `low`
- outputFolder: use the folder requested by the user, otherwise use `Test`

## Image Generation Polling Rule

Image generation is asynchronous. Do not keep polling indefinitely in the same response.

Use this rule for every image task:
1. Start one job.
2. Query the same job at most once immediately.
3. If it is still `running` or `pending`, return the `jobId` and stop.
4. When the user asks to continue/query/check, query that same `jobId`.
5. Do not start a second job for the same request unless the user explicitly requests regeneration.
6. If a PNG already exists for the requested output path, return/list the existing file instead of regenerating.

## Preview-First Rule for Expensive Generation

If the user requests any of the following:

- larger resolution, such as `1536x1024`, `1024x1536`, `2K`, `4K`
- higher quality, such as `medium`, `high`
- polished/final/high-detail output
- expensive batches

then prefer a preview-first workflow unless the user explicitly says to skip preview.

Use:

- `previewFirst = true`
- `previewQuality = "low"`
- `previewSize = "1024x1024"` unless the user explicitly requests another supported preview size
- `finalSize` = requested final size
- `finalQuality` = requested final quality

Workflow:
1. Call `image_assets.start_image_generation_job` with `previewFirst = true`.
2. Call `image_assets.get_image_generation_job` at most once in the same response.
3. If the job reaches `preview_succeeded`, return the preview result and `jobId`, then wait for user approval.
4. If the job is still `running` or `pending`, stop polling and return `jobId`; do not keep waiting in the same response.
5. When the user approves, call `image_assets.promote_image_generation_job` with the same `jobId`.
6. After promotion, call `image_assets.get_image_generation_job` at most once. If it is still running, return `jobId`; if it succeeded, return final `imagePath` and `metadataPath`.

Do not generate the final high-cost image before preview approval unless the user explicitly asks to skip preview.
Do not keep polling indefinitely in one response. This avoids the Codex UI getting stuck on long-running image tasks.

## UI Mockup to Implementation Specification Workflow

A generated UI mockup is a visual proposal, not a direct Unity implementation source.

When the user approves a mockup or asks Codex to implement a Unity UI based on a proposal image, Codex must insert a specification step before modifying Prefabs, scenes, scripts, or Project Settings.

Required workflow:

1. **Mockup / proposal image**
   - Used to communicate the visual direction.
   - May be generated with `image_assets`.
   - Must not be treated as exact RectTransform data.

2. **Structured UI implementation specification**
   - Must be produced before Unity implementation.
   - This is the source of truth for the Prefab implementation.
   - The specification may be returned in chat, and if the user has approved file creation, saved under:
     `Assets/Arts/AI_Generate/_UISpecs/<ui_name>/ui_<ui_name>_spec.md`

3. **Asset manifest**
   - List every required generated image asset before implementation.
   - If saved as a file, use:
     `Assets/Arts/AI_Generate/_UISpecs/<ui_name>/ui_<ui_name>_asset_manifest.json`

4. **Unity implementation**
   - Build or modify Prefabs according to the structured specification, not by visually guessing from the mockup.
   - Use generated assets from the manifest.
   - Preserve existing architecture and serialized references whenever possible.

Do not implement a Unity UI directly from a mockup image without first producing the structured UI implementation specification.

### UI Implementation Specification Requirements

The structured specification must include:

1. **Reference resolution**
   - Example: `1920x1080` for desktop UI, or the project-specific reference resolution if known.

2. **Canvas and scaling strategy**
   - Canvas mode assumptions.
   - `CanvasScaler` reference resolution.
   - Screen Match Mode / Match value recommendation.

3. **RectTransform hierarchy**
   - Root panel.
   - Major regions.
   - Repeated item templates.
   - Buttons, icons, labels, decorative layers.

4. **Anchors and pivots**
   - Anchor presets for each major region.
   - Pivot defaults.
   - Stretch/fixed-width rules.

5. **Approximate sizes, margins, and spacing**
   - Panel margins.
   - Column widths.
   - Card sizes.
   - Padding and spacing.
   - Minimum readable sizes.

6. **Layout components**
   - `HorizontalLayoutGroup`, `VerticalLayoutGroup`, `GridLayoutGroup`, `LayoutElement`, `ContentSizeFitter` usage.
   - Explicitly state where layout groups are avoided and why.

7. **Visual tokens**
   - Background colors.
   - Border colors.
   - Text colors.
   - Opacity values.
   - Font size tiers.
   - Highlight/selected/disabled states.

8. **Asset decomposition**
   - Which visual elements are native Unity UI Images/Texts.
   - Which elements require generated Sprites.
   - Which mockup details are conceptual only and will be simplified.

9. **Responsive behavior**
   - Expected behavior at 16:9, tall mobile, and other relevant aspect ratios.
   - Which panels stretch.
   - Which panels keep fixed width.
   - Which lists scroll.

10. **Implementation risks**
   - Missing scripts or references.
   - Unity MCP availability.
   - Potential visual differences from the mockup.

### UI Implementation Modes

When implementing from an approved mockup, choose one of these modes or ask the user to choose if the intent is unclear.

#### High-fidelity mode

Use this when the user wants the Unity UI to visually match the approved mockup as closely as possible.

Rules:
- Prioritize visual similarity to the mockup.
- Generate additional Sprite assets if needed for frames, card backgrounds, borders, and decorative elements.
- Use more UI Image layers when necessary.
- Still keep anchors and layout groups where possible.
- Explain any remaining differences.

#### Responsive-first mode

Use this when the user prioritizes maintainability and multi-resolution support.

Rules:
- Prioritize anchors, layout groups, scalable spacing, and reusable item templates.
- The UI may differ slightly from the static mockup.
- Explain intentional differences caused by responsive behavior.
- Avoid excessive decorative layers that make the Prefab fragile.

Default mode:
- If the user asks for “尽量接近方案图 / 高还原 / 按预览图实现”, use High-fidelity mode.
- If the user asks for “适配不同分辨率 / 可维护 / 通用”, use Responsive-first mode.
- If both are requested, use a balanced mode and explicitly list the trade-offs.

## Unity Artifact Creation and Verification Rule

When creating or modifying Unity assets such as Prefabs, ScriptableObjects, generated sprites, scenes, or scripts, distinguish between creation result and verification result.

Do not report asset creation as failed only because Unity Console, Unity MCP, batchmode, or validation commands failed.

Use this reporting model:

1. **Created / Modified Files**
   - List actual files that were created or modified.
   - If the expected `.prefab`, `.asset`, `.png`, `.meta`, `.cs`, or `.unity` file exists, report it as created or modified.

2. **Verification Result**
   - Report whether Unity Console, AssetDatabase, script compilation, or MCP validation succeeded.
   - If Unity MCP cannot read Console or batchmode cannot start, report verification as unavailable or failed, not asset creation as failed.

3. **Failure Classification**
   - `Asset creation failed`: expected file does not exist, write operation failed, or file creation returned an explicit error.
   - `Verification failed`: file exists, but Unity validation could not be completed or returned errors.
   - `Unity MCP unavailable`: current Unity Editor connection could not be queried.
   - `Batchmode unavailable`: batchmode could not start; do not infer asset failure from this.

4. **Unity instance safety**
   - If Unity Editor is already open with the project, do not start another Unity instance or batchmode process for verification.
   - Prefer querying the already connected Unity MCP server.
   - If Console cannot be read, ask the user to manually check Unity Console instead of claiming the implementation failed.

## TextMeshPro Initialization and Chinese Font Rule

When creating or modifying Unity UI text, Codex must treat TextMeshPro as a required dependency that needs initialization.

### Mandatory TMP checks before UI implementation

Before creating a UI Prefab that contains text, Codex must check or account for:
1. TMP Essentials are imported.
2. A valid TMP default font asset exists.
3. Every TextMeshProUGUI component has a non-null `font` / `fontAsset`.
4. If the UI contains Chinese text, the assigned TMP font asset must support Chinese characters.

Do not leave any TextMeshProUGUI component with `Font Asset = None`.

### Chinese font requirement

LiberationSans SDF is not sufficient for Chinese UI text. If the UI contains Chinese labels, Codex must prefer a Chinese-capable TMP_FontAsset.

Recommended project-side approach:
1. The user imports a legally usable Chinese `.ttf` or `.otf` font into the Unity project, such as Noto Sans CJK / Source Han Sans / Microsoft YaHei or another permitted Chinese font.
2. Use the package menu: `Tools/AI Image Pipeline/TextMeshPro Setup`.
3. Select the imported Font asset.
4. Click `Create Dynamic Chinese TMP Font From Selected Font`.
5. Set the generated TMP_FontAsset as default and fallback.
6. Repair existing UI texts if necessary.

The package must not assume a Chinese font file is bundled. Do not invent or reference a non-existing Chinese TMP font asset.

### TMP repair rule

If existing UI has TextMeshProUGUI components with null font assets, do not rebuild the whole Prefab. Perform an incremental repair pass:
- find all TextMeshProUGUI components under the target Prefab/root
- assign the project default Chinese TMP_FontAsset if available
- otherwise assign the valid default TMP_FontAsset
- preserve text content, color, size, alignment, RectTransform, LayoutElement, and LayoutGroup settings

If TMP Essentials or a Chinese-capable font asset is missing, report it as `TMP dependency not initialized`, not as UI/Prefab creation failure.

### TMP + LayoutGroup safety rule

TextMeshProUGUI inside HorizontalLayoutGroup, VerticalLayoutGroup, GridLayoutGroup, or ContentSizeFitter must always have a valid font asset before layout rebuild.

A missing TMP font can trigger NullReferenceException during layout calculation, especially when Unity calls:
- `preferredWidth`
- `preferredHeight`
- `LayoutUtility.GetPreferredWidth`
- `LayoutRebuilder.Rebuild`

If this error appears, fix TMP font assignment first. Do not redesign or regenerate the UI unless there is a separate layout problem.

```json
{
```

## v1.9 Safety And Diagnostics Rules

### Image MCP health check first

Before generating images in a newly opened Codex session, prefer calling `image_assets.health_check` once. This tool only returns configuration and safety limits; it must not generate images.

Use `health_check` when:
- the user asks whether image2 / image_assets is available;
- Codex has just reconnected;
- the output root, provider, model, proxy, or API key status is uncertain;
- the user asks to diagnose MCP setup.

Do not use image generation as a health check.

### Cost guardrails

Respect the MCP server limits reported by `health_check`:
- `maxJobsPerSession`
- `maxAssetsPerManifest`

Default behavior:
1. Generate only the minimum required assets for the current task.
2. Use preview-first for high-cost images, important UI mockups, large backgrounds, final icons, and any prompt that may require multiple attempts.
3. Do not batch-generate large icon sets unless the user explicitly approves the manifest.
4. When a manifest contains many assets, ask for confirmation and generate in small batches.

### Persisted job awareness

Image generation job state may be persisted under the generated output root. If a job cannot be found in memory after reconnect, call `get_image_generation_job` with the original `jobId` before starting a new job.

### Unity MCP read-only boundary

The setup tool may configure a `mcp_unity` Codex server, but image generation tasks still must not modify Unity scenes or assets by default.

Allowed by default:
- read Unity scene information;
- read GameObject / Component information;
- read Console errors and warnings;
- inspect whether generated assets exist.

Forbidden unless the user explicitly authorizes a write operation:
- modify Scene files;
- modify Prefabs;
- modify ScriptableObject assets;
- modify ProjectSettings;
- create or delete GameObjects;
- save scenes;
- run PlayMode automatically.

### Short trigger words

Recognize these compact modes when the user uses them:

- `@image`: image resource planning or generation. Start with manifest or health check when appropriate.
- `@read`: read-only inspection. Do not modify files or generate images.
- `@plan`: planning only. Do not call image generation unless explicitly approved.
- `@review`: review only. Do not modify files.
- `@do`: limited execution. Only perform the specific approved change.
- `@handoff`: produce a handoff summary without modifying files.

When `@image` is used for a new asset, first infer `outputFolder`, `assetName`, `assetType`, `style`, `usage`, and whether preview-first is needed. If any critical field is ambiguous, choose a safe default and state it briefly.
